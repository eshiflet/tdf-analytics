# TDF Analytics

Interactive Tour de France GC and Points classification visualizer, covering all 66 editions from 1960–2025. Live at **[ericshiflet.com/tdf-analytics/](https://ericshiflet.com/tdf-analytics/)**.

---

## Project Overview

The app shows each rider's rank (GC position or sprint points standing) after every stage of a selected Tour de France year, rendered as a bump chart. Users can switch years, toggle between GC and Points classification, search for riders, and hover stages/riders for detail.

**Tech stack:**
- Frontend: Vite + TypeScript + D3 (static site, no framework)
- Data: SQLite → Python export → JSON files bundled by Vite
- Hosting: GitHub Pages, deployed via GitHub Actions on every push to `main`

## Data Pipeline

Data flows in one direction:

```
PCS website  →  raw tdf_*.json (scraped via Chrome)
                    ↓
             build_db.py  →  cycling.db
                                  ↓  (+ sprint_points.json, profile_icons.json)
                            export_gc.py  →  src/data/gc_by_stage_YEAR.json  (×66)
                                                        ↓
                                              vite build  →  build/  (deployed)
```

### Key data files

**`cycling.db`** — SQLite database with tables:
- `race_editions` (year, edition_id)
- `stages` (stage_id, edition_id, stage_number, start/finish location, distance_km, vertical_meters, route_type)
- `riders`, `teams`, `countries`
- `stage_results` (rider_id, stage_id, gc_rank, gc_gap_seconds, status)

**`sprint_points.json`** — Green jersey sprint points scraped directly from PCS stage pages. Structure:
```json
{ "2025": [ {}, {"rider/jonathan-milan": 12, ...}, ... ] }
```
Array index = stage position in DB ordering. Each dict maps `rider/rider-slug` → points earned that stage from intermediate sprints + stage finish (exclude KOM sprint points). Data starts at 1964 (PCS has no sprint sub-tables for 1960–1963).

**`profile_icons.json`** — Stage route type (F=flat, H=hilly, M=mountain, TT=time trial, TTT=team TT) scraped from PCS route/stages pages. Same array-index convention as sprint_points.json.

**`gc_by_stage_YEAR.json`** — One per year, imported by Vite and bundled into the JS output. Structure:
```json
{
  "stages": [{ "stage_number": 1, "start_location": "...", "finish_location": "...",
               "distance_km": 185.5, "vertical_meters": 1200, "route_type": "F" }],
  "riders": [{
    "id": "rider/tadej-pogacar",
    "name": "Pogačar Tadej",
    "nationality": "Slovenia",
    "team": "UAE Team Emirates",
    "finalRank": 1,
    "byStage": [{ "stage": 1, "gcRank": 5, "gcGapSeconds": 12, "status": "FinishedStage",
                  "cumulativePoints": 0 }]
  }]
}
```

## Deployment

Push to `main` and GitHub Actions handles the rest:
```bash
git add .
git commit -m "describe your change"
git push
```

The workflow (`.github/workflows/deploy.yml`) runs `npm ci && npm run build` inside `cycling-app/`, then deploys `cycling-app/build/` to GitHub Pages. Live in ~2 minutes.

> **Note:** `vite.config.ts` has `base: "/tdf-analytics/"` — this must stay set or asset paths break on the deployed subpath.

## Adding a New Year (e.g. 2026 Tour)

1. **Scrape the raw data** from procyclingstats.com via Chrome DevTools. The scraper pattern used previously fetches stage-by-stage classification data from PCS stage pages (see build_db.py comments for the expected JSON shape).

2. **Add sprint points** for the new year to `pipeline/sprint_points.json`. The key is the year string; value is an array of dicts (one per stage) mapping `rider/rider-slug` → points earned that stage from intermediate sprints + stage finish (exclude KOM sprint points). See existing entries for format.

3. **Add profile icons** for the new year to `pipeline/profile_icons.json`. Array of route type strings per stage.

4. **Rebuild the database:**
   ```bash
   cd pipeline
   python3 build_db.py      # ingests tdf_2026_full.json → cycling.db
   ```

5. **Re-export JSON files:**
   ```bash
   python3 export_gc.py     # writes cycling-app/src/data/gc_by_stage_2026.json
   ```

6. **Push** — the app auto-discovers all years from the bundled JSON files (no hardcoded year list).

## Key Implementation Notes for Claude

**GC ranking algorithm:** PCS data for older years (pre-1995) sometimes has gaps, ties, or missing cumulative times. `build_db.py` uses a hybrid approach: anchor confirmed PCS-published top-N rankings, then fill gaps by reconstructing cumulative time from stage gaps. See the large comment block in `build_db.py` around `compute_gc_rankings()`.

**Sprint points vs. PCS points:** The DB has a `pcs_points` column which is PCS's prestige/ranking system — completely unrelated to the green jersey. Green jersey sprint points come exclusively from `sprint_points.json`, scraped from PCS stage sub-tables labeled "Sprint | location" (intermediate) and "Points at finish" (stage finish). KOM sprint sub-tables (labeled "KOM Sprint...") are excluded.

**1988 Prelude:** PCS lists 23 entries for 1988 on the route/stages page — the first is an unofficial "Prélude" stage. The scraper drops index 0 for that year; profile_icons.json and sprint_points.json do the same.

**Stage numbering:** The `stage_number` field in the DB matches PCS's ordering. Split stages (e.g. 1a/1b) each get their own stage_number. The JSON array index in sprint_points.json and profile_icons.json corresponds to DB stage ordering (not stage_number value).

**Metric dropdown:** The app supports two metrics — `gc` (GC position) and `points` (cumulative sprint points standing). State is managed in `main.ts` via `currentMetric`. Points rankings are computed client-side in `computePointsRankings()` from the `cumulativePoints` field on each `byStage` entry.

**Vite data import:** All 66 JSON files are imported via `import.meta.glob('./data/gc_by_stage_*.json')` in `main.ts`. This bundles everything into the JS output at build time — no runtime fetching.
